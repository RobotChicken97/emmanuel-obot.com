I Kept Adding Rules for My Coding Agents. Then I Had to Take Most of Them Out

Last December, when I started building our pharmacy’s stock system on ERPNext, the first instructions I gave the coding agent fitted in about 3 KB. There was a short file on how to run the project and what not to touch, and a nine-line file of notes on using AI in the repo. One of those nine lines said to keep entries short and “prune/replace older items to prevent doc bloat”. I’d like to say I followed that advice.

Coding agents like Codex read a file called AGENTS.md at the start of every task. It’s where you tell them how the project works, what they mustn’t do and how to check their work. Over the next few months I built a lot of other things around that file: scripts the agent had to run, checks before a change could merge, review loops, status files, even a memory file. People call all of that, everything apart from the model itself, a harness.

I ended up with quite a big one, across three repos: the pharmacy server, the till app for the shop counter, and an ERP I built for a manufacturing client. Then I spent a good part of this year taking it apart again.

Every mistake turned into a rule

The first thing I tried was memory. I wanted the agent to learn from its mistakes, so it kept a file of what it had learnt. Within a couple of months that file was about 74 KB, and an audit the agent ran on it put the noise at 94%, mostly file paths. I took the memory data out of the repo the next day.

The rules went the same way, just more slowly, because of how I was using them. An agent did something wrong, I noticed, and I asked for a rule so it wouldn’t happen again. By spring the server’s AGENTS.md was about 17 KB. I started the till app with a 2.4 KB file, and less than a month later it was 23 KB.

By the summer I was running one agent as an orchestrator, a session whose only job is to hand tasks to other agent sessions and check what comes back. One day it started writing the code itself. I asked whether it had forgotten, and whether we needed to update its AGENTS.md. A few minutes later I asked for a guard to make sure it didn’t forget who it was. I said I hadn’t wanted a hard guardrail, but I thought this one was needed.

When I started the client ERP in June, it began with all of this already in place. Its AGENTS.md was 238 lines and about 20 KB on the first day, and 30 KB less than two weeks later. There were hooks that ran before commands, checks before merging, and a shared status file, a log of where everything stood, that most changes had to update. That month, 101 of the 132 pull requests we merged edited that status file.

And to be fair, it worked well for a while. In its first week I wrote that the orchestrator setup had transformed the way I worked, mostly by turning my lazy descriptions into proper tasks, and that it often found better approaches than I would have thought of. I still think that part was right.

The review loop that never finished

Every pull request went to Codex’s code reviewer on GitHub, and it couldn’t merge until the reviewer’s comments were dealt with. Each fix was a new change, and the reviewer looked at that too. It was the part of the harness I was proudest of.

The cost showed up early. When I read OpenAI’s post on harness engineering, I typed that the team who wrote it “have unlimited tokens to burn, I don’t.” The same day I noticed every change in our pull requests was additive and asked whether we ever cleaned anything up. We didn’t, much.

A couple of weeks later I had the agent pack up the review history so I could ask a different model what was going wrong. The brief it wrote already named the review loop as the problem. I didn’t fully act on that until the end of the summer.

So the loop kept going, and it got a bit silly. One week I counted seven pull requests all doing the same thing, each one opened to replace the last after the comments piled up. By then the reviewer had been through 245 pull requests and left 1,459 comments, and 79 of those pull requests were closed without ever merging. I pointed out to the agent that I’d built all of this to get out of endless review loops, and now we were stuck in another review loop.

A new model, and a much shorter rules file

When OpenAI released GPT-5.6 Sol in July, I asked it to read the prompting guidance for the new model and rewrite our rules and skills for itself, since they’d been written for an older model.

I also asked something I should probably have asked a month earlier. If you give a model this good the job of finding bugs, it will always find bugs. So were we chasing a carrot that would never converge?

Within the week the review gate script was gone and the rules had come down in all three repos. The client ERP’s AGENTS.md went from about 25 KB to 6 KB, and the other two came down to 7 or 8 KB.

The pull request that simplified the review loop couldn’t get through the review loop. It went five rounds and picked up 13 more comments.

In the end I accepted it by hand.

Then the weight moved somewhere else

The rules file was small now, so the rules went somewhere else. Before an agent could write code for a feature, it had to write a “source readiness” contract saying exactly what it would build and how it would prove it, and the contract had to be reviewed until it was ready.

I could see it happening, which makes it worse. I asked for an audit of whether the whole setup was overengineered, and the next day I asked that same audit the same question three times. A week later one contract grew from 816 lines to 2,818 in about a day.

By late August the harness files in the client ERP had gone from under 1 MB to about 4.5 MB. Each Codex thread I started that month used about 52 million tokens on average, against 10 to 20 million in the other months. Most of that was cached input, the same rules and files read again and again, so it isn’t a bill of that size. It was still where a lot of my time and usage went though.

Taking most of it out

Near the end of August I stopped a task on the pharmacy server that had somehow got into Docker TLS settings. I wrote that we were definitely doing too much, and that this brittle setup was causing too many problems. The agent’s view was that we’d retired the harness by name, but its habits had come back inside individual tasks.

The client ERP’s clean-up had been waiting a couple of weeks, and the next day it went in. Its pull request deleted 585 files and about 196,000 lines: the old staging and proof scripts, the status workbook, a second copy of the review process, a folder of generated evidence, the 2,818-line contract, and a layer of tests that only checked the shape of the source code.

Then I worried I’d gone too far. With review loops turning up again, I asked whether the harness had been useful after all and whether we needed parts of it back. A few days later I took Codex’s GitHub reviewer out of the process as well. In its place there’s one fresh review by a separate agent, plus the normal automated checks.

Before the cut, one pull request in ten took more than 9.5 hours to merge, and in September that was down to an hour. That’s a rough measure, and other things changed in September too. Pull requests closed without merging went from 65 in June to none in September.

Bits of it hung on, though. A few weeks later I was asking why seeding some test data had turned into 12,000 lines and counting, and in October I found one of the hooks the client ERP had started with still refusing commands just because they mentioned a protected folder.

The pharmacy repos got stuck

The pharmacy repos hadn’t had a clean-up like that, and they ended up worse. Neither of them merged anything for more than five weeks. Some of that was me holding the pharmacy work back to save tokens, but the till app merged only two pull requests in about two months.

So in October I asked for an audit of where the work was going. On one day, only 17% of the tokens Codex used went on the product, and none of the seven pull requests it merged was a feature. The till app had more lines of scripts around it than lines of product code.

The clearest sign was the soak test, the eight-hour run that’s meant to show the till can trade all day. It was pointed at a backend address it couldn’t reach, so it sat on a diagnostics screen for eight hours and never made a sale. One pull request, for paying with more than one method, had collected 157 reviews and still hadn’t merged.

The fix that day was a one-line decision taking the pharmacy repos out of the readiness rule, and a much shorter rules file for each of them. Among the new rules are “Fix the product, not the harness”, “A test runs code” and “A soak must transact”. Every guard has to name the decision it protects, and comes out when that decision changes. In the nine days after that, the till app merged 45 pull requests. Claude had also taken over the till work that day, so it wasn’t only the rules.

The new models were only part of it

When I started writing this, I thought the rewrites had often come with a new model. I’d even written that we retired the harness “due to upgrading models and better intelligence”. Going back through the chats and the commits, that’s only partly right.

New models did start a lot of the rewrites, including the July cut. In September GPT-6 Astra and GPT-6.1 Sol each started another pass over the rules, but none of those passes made them shorter overall, and two of the files got longer. The big clean-up at the end of August came six or seven weeks into the same model. The October cuts came after I started using Claude, and I switched because a Codex thread was stuck and I’d hit my token limits. Claude’s model had been out for nearly four weeks by then.

Where I think a better model did change things was review. The loop was already stuck before Sol came out. But a stronger reviewer finds more, so after that a rule like “review until clean” only got harder to finish.

Anthropic has a good write-up on harness design that treats each part of a harness as a bet on something the model can’t manage on its own yet, which is worth checking again whenever a new model comes out. That doesn’t make harnesses useless. Naresh Jain ran an experiment where coding agents built the same service with and without one. On the strongest model the harness cost about seven times as much per run, and 10 out of 10 runs passed either way. On a cheaper model it took the pass rate from 3 to 10 out of 10.

Where I’m at with it now

The client ERP’s AGENTS.md is now about 7.6 KB and hasn’t changed in roughly 620 merged pull requests. It keeps the product safety rules, one fresh review before merge, a stop after three rounds of review that don’t settle, and a line about making the smallest change that does the job. A few of the rules only say what not to add.

In June, 42% of the pull requests merged in the client ERP were product work, though it was still partly a planning repo then. So far in November it’s 98%. Between June and now I changed the model, the tool, the rules and the way changes were merged, so I can’t credit any one of them, but the work is going into the product now.

Rules still try to grow back. The till app’s file has crept up to about 12 KB against a target of 4 KB, and I’ve caught myself asking whether we should tell the auditor that finding no issues is an acceptable answer. I’d like to get that file back down to its target next, using the same test as the pharmacy repos, where every guard has to name the decision it protects.

Looking back, the most useful rule in the whole harness was probably in that first nine-line file from December. Keep entries short, and prune or replace older items to prevent doc bloat. It took me about ten months to start following it.
